01 / Runtime summary

One manager, several bot implementations

The game does not call strategy code directly from the lobby. The lobby stores AI difficulty and optional custom bot identity in game options. At game start, BotManager creates one bot per AI combatant, injects APIs, and owns the per-tick/event dispatch.

Orchestration

BotManager is the runtime boundary. It creates bots, subscribes to game events, drains the action queue, calls lifecycle methods, logs failures, and disposes subscriptions.

Decision makers

BuiltInBotAdapter wraps the full mission/strategy AI. ThirdPartyBotAdapter wraps a registered uploaded bot. DummyBot is the lightweight fallback for the other legacy difficulty values.

Command boundary

Bot reads go through GameApi, PlayerApi, and ProductionApi. Commands go through ActionsApi into ActionQueue, then are processed by the simulation.

03 / Lifecycle

What happens at start and on every tick

The manager isolates each bot call with error handling. One bot failing does not abort the whole game update or prevent other AI players from being serviced.

04 / Bot selection

Difficulty is a factory decision

The player record contains isAi, aiDifficulty, country, and optional customBotId. BotFactory.create() maps those values to a concrete Bot subclass.

InputFactory resultBehaviorFallback / failure
Normal BuiltInBotAdapter Full built-in strategy with awareness, missions, production, and attack/defence decisions. The adapter has a low-frequency fail-safe for MCV deployment, structure production, and placement.
Custom + valid customBotId ThirdPartyBotAdapter Instantiates the selected registry metadata factory for this player. If the ID is absent from the registry, the factory tries the first uploaded bot.
Custom + no usable upload BuiltInBotAdapter Preserves a playable AI when custom selection has no available custom implementation. Logs a warning: custom AI selected but no uploaded bot found.
Easy, Medium, MediumSea, or Brutal DummyBot Small state machine: deploy MCV, wait, and resign when no selectable combatants remain in its attacking state. These are supported by the factory even though the current lobby UI primarily exposes Easy, Normal, and Custom.
Non-AI player or unknown difficulty None Human players are never passed to the bot factory. Non-AI or unsupported values throw from BotFactory.create(). 
if (player.aiDifficulty === AiDifficulty.Custom) {
  const meta = registry.get(player.customBotId);
  if (meta) return new ThirdPartyBotAdapter(player.name, player.country.name, meta);
  if (registry.getUploadedBots().length) return new ThirdPartyBotAdapter(...);
  return new BuiltInBotAdapter(player.name, player.country.name);
}

05 / Built-in AI

Awareness feeds missions, strategy, and queues

The built-in implementation is a layered controller. Its outer adapter preserves the common Bot contract; the inner BuiltInBot owns the actual strategy state and schedules work at a bot-specific rate derived from game tick rate and a 300 APM target.

Match awareness

MatchAwarenessImpl updates sector visibility, build-space cache, scouting, hostile-unit spatial index, global threat, rally point, and expansion candidates. Threat is recalculated every 30 ticks; rally points every 90; expansion candidates every 240.

Default strategy

DefaultStrategy may create expansion, scouting, attack, defence, and engineer missions. Attack compositions are selected from valid faction-specific compositions using the game random source.

Mission controller

MissionController owns active missions, removes dead units, resolves priority requests, assigns free units, updates debug labels, and batches compatible orders through ActionBatcher.

Queue controller

QueueController evaluates structures, armory, infantry, vehicles, aircraft, and ships. It queues requested objects, places ready buildings, pauses low-priority production, resumes useful queues, and repairs damaged objects.

Built-in tick order

On its scheduled tick, BuiltInBot attempts initial MCV deployment, updates awareness, checks its resign condition, updates missions and strategy every three AI updates, then lets the queue controller reconcile production. The adapter runs its fail-safe after normal logic, including when normal logic throws.

  • BuiltInBot.tsTop-level lifecycle and scheduling.
  • awareness.tsMap, visibility, threat, scouting, expansion.
  • defaultStrategy.tsMission factories and compositions.
  • missionController.tsMission and unit assignment.
  • queueController.tsProduction and building placement.
  • BuiltInBotAdapter.tsCommon bot adapter and fail-safe.

06 / Custom bots

Upload, validate, load, register

Custom bots are browser-side scripts packaged in a zip. The uploader extracts the archive without a third-party zip dependency, validates its shape and source, then evaluates the main script in a deliberately restricted function scope.

A

Accept only a bounded archive

BotUploader.processUpload() requires a .zip no larger than 10 MB. The extracted content is capped at 200 files, with a 512 KB maximum per file and a 10 MB total extracted size.

B

Find the entry point

The archive must contain bot.ts or index.ts at the root or one directory below it. Allowed extensions are .ts, .json, .txt, .md, and .yml; path traversal names are rejected.

C

Strip lightweight TypeScript syntax

BotSandbox.stripTypes() removes interfaces/type blocks, imports, casts, parameter and variable annotations, access modifiers, enums, and non-null assertions. It is a lightweight source transform, not a general TypeScript compiler.

D

Reject known dangerous patterns

Source scanning blocks patterns for dynamic code, network access, storage, DOM/window access, Node process/module access, filesystem operations, and prototype-constructor escape attempts.

E

Evaluate and require the export contract

The script is executed through new Function() with a narrow injected global set such as Math, Date, collections, JSON, and prefixed console methods. The result must expose id and createBot. A registry metadata object is then created and stored with the source for persistence.

Security boundary

This is source filtering plus restricted scope, not a hardened security sandbox. The forbidden-pattern list is intentionally visible in BotSandbox.ts. Do not treat uploaded bot code as trustworthy or expand the allowed surface without reviewing the threat model.

Third-party export shape

// bot.ts or index.ts
module.exports = {
  id: "my-bot",
  displayName: "My Bot",
  version: "1.0.0",
  author: "Author",
  description: "Short description",
  createBot: function (playerName, country) {
    return {
      onGameStart: function (ctx) { /* initialize */ },
      onGameTick: function (ctx) { /* decide + issue actions */ },
      onGameEvent: function (event, data) { /* react */ },
      dispose: function () { /* optional cleanup */ }
    };

07 / Bot API

Read through APIs, write through actions

The bot is not expected to mutate the world directly. It queries a projection of game state and emits actions that the simulation validates and executes.

SurfacePurposeRepresentative operations
GameApi Read global match state and map/rules data. getCurrentTick(), getPlayerData(), getVisibleUnits(), getGameObjectData(), canPlaceBuilding(), getGeneralRules(), mapApi, random helpers.
PlayerApi Read state scoped to the bot's player. getPlayerData(), isDefeated(), isAlliedWith(), canPlaceBuilding(), getVisibleUnits().
ProductionApi Inspect available objects and production queues. getAvailableObjects(), getQueueData(), isAvailableForProduction().
ActionsApi Translate intent into game actions. orderUnits(), queueForProduction(), placeBuilding(), pauseProduction(), resumeProduction(), activateSuperWeapon(), sayAll(), quitGame().
LoggerApi Write bot-scoped diagnostics, with debug level controlled by manager debug selection. info(), error(), and other logger methods exposed through the injected logger.
Adapter context shape

The common TypeScript interface names the callback argument gameApi, but ThirdPartyBotAdapter actually passes a context object: { gameApi, actionsApi, productionApi, logger, playerName, country }. The supplied example bot uses this context shape.

// Typical custom bot tick
var ctx = { gameApi: gameApi, actionsApi: actionsApi, productionApi: productionApi, logger: logger, playerName: playerName, country: country };
var enemies = ctx.gameApi.getVisibleUnits(ctx.playerName, "enemy");
if (enemies.length) {
  var target = ctx.gameApi.getGameObjectData(enemies[0]);
  ctx.actionsApi.orderUnits(myUnits, OrderType.AttackMove, target.tile.rx, target.tile.ry);
}

09 / Current notes

Important implementation details

Legacy shells remain

game/ai/Ai.ts currently only stores the AI INI object and exposes getIni(). BotsLib.ts is an empty class. Neither is the active decision loop documented above.

External bot library loading

GameLoader.loadBotsLib() attempts to load @chronodivide/sp-bots and passes its result as botConfig into GameFactory. The current local BotFactory chooses from built-in and registry adapters instead of consulting BotsLib directly.

Debug focus follows one bot

BotManager listens to botDebugIndex, resolves an AI player name, and toggles debug mode on exactly the matching bot. Built-in debug text can then be written through debug actions and its internal buffers.

Failure isolation is intentional

Manager-level catches isolate bot creation, initialization, event, and tick errors. The built-in adapter adds a fail-safe after normal logic. Custom adapter tick errors are logged periodically to avoid flooding output.

Maintenance rule

If any of the paths or lifecycle boundaries above move, update this HTML document alongside the TypeScript change. The source links are intentionally local so the page remains useful from a checked-out repository without a documentation server.

10 / Upstream multiplayer

Same strategy, different multiplayer runtime

The local built-in bot is adapted from Supalosa's Chrono Divide bot. The decision system is similar, but the upstream project demonstrates a separate online bot agent while this codebase embeds bots inside each local game simulation.

Upstream online agent

packages/chronodivide-bot-driver/src/index.ts calls cdapi.createGame() with online: true and a bot in the agents list. The bot runs in a Node process, connects as an online player, and updates its own game agent until the match finishes.

Upstream driver source

Local lockstep AI

GameFactory creates one BotManager for each Game. On every multiplayer peer, that manager creates one bot per AI combatant and runs the bot locally during Game.update().

Local GameFactory source
Instance isolation rule

Each bot owns mutable match state: missions, threat caches, production decisions, assigned units, rally points, and debug buffers. Never share a bot instance between games or between AI players. In local multiplayer, every peer has its own equivalent bot instance and must run the same deterministic logic.

Custom bot multiplayer requirement

The local lobby synchronizes game options, not uploaded bot source. Every peer must have the same custom bot registered under the same ID. Otherwise peers can select different implementations and diverge from the lockstep simulation.
